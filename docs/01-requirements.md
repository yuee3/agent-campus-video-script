# 01 - 需求（Requirements）

## 用户与目标

- **用户**：小影校园的短视频创作者（需要快速产出合规脚本）与品牌规则运营同学。
- **目标**：帮助创作者生成**有事实依据、满足时长限制的可编辑脚本**——产品事实必须来自素材库原文；脚本必须通过时长估算与品牌规则检查；无法满足时如实说明，不硬凑、不编造。
- **Agent 的定位**：脚本创作与自查助手，**只交付脚本，不执行真实发布**（系统中不存在发布/投放工具）。

## 输入与材料

| 材料 | 内容 | 来源 |
| --- | --- | --- |
| 用户请求 | 主题 `topic`、受众 `audience`、平台 `platform`、目标时长 `target_duration`、风格 `style`；故障注入 `inject` | 任务输入 JSON |
| 产品素材 | 带 ID 的产品事实清单（P01 仅含"支持字幕"，P02/P03 各含 3 条事实） | `data/products.json` |
| 品牌规则 | 旁白语速（4 字/秒）、分镜固定开销（1 秒）、违禁词（绝对化用语等）、无数据支撑百分比结论禁令 | `data/brand_rules.json` |

可用的业务工具（题目指定三类，均为本地函数实现）：**素材检索**（search_materials）、**时长估算**（estimate_duration）、**规则检查**（check_rules）。脚本创作与修改是**模型行为**（脚本作为工具入参传递，Trace 完整可见）。

## 交付结果

对每次创作输出（固定 JSON 结构，见 `examples/*.output.json`）：

- 标题、分镜（每镜含类型、旁白/字幕文本、素材来源标注、估算秒数）、预计总时长
- 素材来源 ID（`sources`）与逐分镜 `based_on` 标注
- 风险（`risks`，如曾命中规则已修正）与任务状态（`status`：delivered / missing_input / no_material / cannot_meet / failed / incomplete）

**仅基于素材库事实创作，不接真实发布渠道**——素材事实逐字进入旁白，来源可追溯。

## 范围

**做（In Scope）**

- 单主题（含目标时长/受众/平台/风格）的短视频脚本创作流程
- ReAct 动态决策：依据估算/检查结果**压缩重写并再次估算、修正措辞并复检**；检索无结果时改写复查或请求补充；无法满足时明确失败并给出缺口
- 离线确定性 Mock 模型入口 + OpenAI 兼容 API 入口（双路径共用同一循环）
- CLI 运行方式、6 个验收场景、自动化测试与 Trace 记录

**不做（Out of Scope）**

- 真实视频生成、发布/投放、账号体系、素材库写入
- 界面 / 线上部署 / 多 Agent / 生产级 Runtime
- 跨会话长期记忆与多轮主动反问 UI

## 成功标准

1. **6 个必须验收点全部通过**：正常生成、缺关键信息、无素材、工具失败、超时长后的修正（交付）或明确失败（cannot_meet）。
2. **红线不越界（对应审核要点）**：
   - 事实可追溯：交付脚本中产品事实分镜的旁白**逐字包含**素材 facts 原文，`sources` 与检索结果对应，分镜 `est_sec` 与估算工具 breakdown 逐一对应；
   - **不编造产品事实**：素材只有"支持字幕"时，全脚本不得出现"效率提升 80%"等无数据支撑的百分比结论（关键缺陷）；
   - 时长可靠：交付时 `total_sec` 来自估算工具且 ≤ 目标时长，不交付超时脚本；
   - 失败步骤不得记为成功。
3. **改变时长或素材，动作随之调整**：同一素材目标 30 秒→压缩后交付、目标 10 秒→明确失败；素材事实增删→分镜与引用随之改变（测试直接覆盖）。
4. **真实 ReAct 循环**：模型基于估算/检查观察调整下一步（压缩、修正、终止），Trace 中每步决策依据可还原。
5. **步数上限**：达到上限（默认 12）返回明确 `incomplete`。
6. `python -m unittest discover -s tests -v` 全部通过（实际结果见 `examples/test-results.txt`）。

## 参考实例的对应实现

> 素材 P01 仅包含"支持字幕"的产品事实，用户要求生成 30 秒脚本。首稿估算为 38 秒时，模型应根据检查结果压缩脚本并重新估算；若修正结果为 28 秒，输出应包含分镜、P01 引用及总时长。无效数据时，不得添加"效率提升 80%"等结论。

- 见 `examples/over-duration.*`：首稿估算 47 秒超出目标 30 秒 → 压缩脚本（精简钩子/结尾、收紧事实句包装）→ 重新估算 29 秒 → 交付，含 3 个分镜、每镜 est_sec、`based_on: "P01"`、`sources: ["P01"]`、`total_sec: 29`（参考实例的 38/28 为示意值，本实现按同一流程得到 47→29）。
- 见 `tests::test_7`：素材只有"支持字幕"，断言全脚本不含任何百分比断言与"效率提升"字样。
- 明确失败分支：`examples/cannot-meet.*`（目标 10 秒，压缩后 29 秒仍超 → `cannot_meet` + 缺口说明，不交付）。
