# 05 - 复盘（Retrospective）

## 最难的三个问题

**1. "有效修正"怎么才不是预设分支？**
最初考虑让 estimate_duration 直接返回 `over_target: true`，但这样"是否超时长"的判断就沉进了工具层，模型只是转发结论——恰恰落入"固定条件分支不视为 ReAct"的否定项，也经不起审核要点"改变时长，核对下一步动作是否调整"的检验。最终让工具只返回时长事实（total_sec + 逐分镜 breakdown），对比目标、决定压缩、复算缺口（29−10=19 秒）全部由模型完成：同一素材 30 秒走"压缩后交付"、10 秒走"明确失败"，动作随输入真实变化。

**2. "编造产品事实"怎么在结构上堵死，而不只是写在 Prompt 里？**
审核要点把编造列为关键缺陷，参考实例特意用"只有一条事实的 P01"来诱导模型脑补"效率提升 80%"。我的做法是把脚本生成约束成"模板 + 素材事实逐字嵌入"：模板措辞（钩子/结尾）不含任何产品信息，所有产品陈述只能来自 facts 原文——素材里没有的数据在结构上写不出来，测试再对全脚本断言无百分比结论。Prompt 纪律是第二道防线，结构保证才是第一道。

**3. 规则修正后怎么避免"对旧观察反复修正"的死循环？**
开发中真实出现过：检查命中"最"（误伤"看到最后"）→ 修正 → 重新估算 → 模型再次读到同一条 violations 观察 → 再修正……直到步数上限。根因是状态机用"是否存在 violations 观察"决策，而该观察在版本更新后已经过时。修正为**版本化自查**：以"当前版本文本是否已检查过"（check 入参与当前全文比对）决策——新版本未查过就查、查过且命中才修正、修正两次仍命中如实终止。这让我体会到：Loop 里"记忆"的正确粒度是"观察 + 产生该观察时的动作入参"，只有观察没有入参就无法判断观察是否还有效。

## 学习收获

- **事实与判断分离同样适用于创作类任务**：估算/检查工具给事实，压缩、修正、终止的决策归模型——"有效修正"的含金量来自决策链路的真实性。
- **编造的防线要建在数据流上**：模板 + 事实逐字嵌入的设计让"编造产品事实"从"靠模型自觉"变成"结构上不可能"，测试只需验证数据流不变量。
- **调试 ReAct 状态机要看动作入参**：Trace 里同时记录 action（含 args）与 observation，是定位"观察过期"类 bug 的关键。

## 下一步（按优先级）

1. **接入真实模型验证**：用 `AGENT_MODEL=api` 跑通同一组验收用例，对比 Mock 与真实模型的脚本质量与修正行为；为 API 模式增加输出 JSON 校验与格式漂移重试。
2. **时长估算精细化**：支持语速参数按平台/风格调整、口播停顿与 BGM 卡点建模，估算与真实剪辑对齐。
3. **规则修正回流**：把修正记录回写品牌规则知识（如高频误伤词加白名单），形成反馈闭环。
4. **pass^k 稳定性**：同一用例重复运行 k 次验证真实模型下的稳定性（对 Mock 无意义，对 API 模式必要）。
5. **脚本版本 diff 交付**：交付物附首稿与终稿的逐镜对比，方便创作者理解"为什么压缩了这些"。
