# 04 - AI 使用（AI Usage）

> 本文档如实记录 AI 辅助的范围、个人贡献与验证方式。评审者可对照 git 历史与 Trace 交叉验证。

## AI 辅助的范围

本项目在 AI 辅助工具（编码智能体）支持下完成，具体分工如下。

**AI 承担的部分**

- 依据候选人的设计方案生成项目脚手架与全部代码：工具层（2-gram 检索打分、时长估算公式、规则匹配、单次故障注入）、ReAct 循环、Mock/API 双模型入口、CLI、Trace 记录
- 生成 6 个验收场景的测试代码与合成数据（3 个产品素材、品牌规则表，含参考实例的 P01"仅支持字幕"）
- 生成 examples/ 的实际运行输出、Trace 与测试记录
- 起草 docs/ 五篇文档与 README

**候选人承担的部分**

- 题目理解与验收标准确认：把题目 5 个必验收点 + 审核要点（素材 ID/分镜时长/检查结果逐一对应、改变时长或检索结果核对动作调整、有效修正与事实可追溯、编造产品事实属关键缺陷）转成可断言的成功标准
- 核心设计决策（见 [02-solution.md](02-solution.md)）：
  - 选定"原生实现 + CLI + Mock/API 双入口"的技术路线与边界声明
  - **事实与判断分离**：估算只给时长事实、检查只报命中，超时压缩、缺口计算、措辞修正全部留在模型侧——保证"调整脚本并再次检查"是真实的动态决策
  - **编造阻断的结构设计**：脚本 = 模板 + 素材 facts 逐字嵌入，模板措辞不含产品事实；百分比结论在素材无数据时结构性写不出来
  - 版本化自查（按"当前版本文本是否已检查"决策，防止对旧观察重复修正）
- 设计评审与修正（AI 生成的代码经候选人评审后修正了 3 处真实缺陷）：
  - 修正 check_rules 状态机死循环（修正后未对新版本文本复检，导致对同一 violations 观察反复修正直至步数上限）
  - 修正 `checked_current` 从观察结果（observation）取入参的错误——入参应从动作（action）取
  - 修正品牌规则"最"字误伤"看到最后"的误报（改为精确词组匹配）
- 逐项验证（见下节）
- 本文档及各文档的核对修订

## 验证方式

AI 生成的产物不默认可信，按以下方式验证：

1. **自动化测试**：`python -m unittest discover -s tests -v`，11 个用例覆盖 5 个必验收点 + 编造红线 + 步数上限 + 内容替换鲁棒性 + CLI 边界，实际结果见 [examples/test-results.txt](../examples/test-results.txt)。
2. **红线核对**：对全部场景断言事实逐字可追溯、无百分比编造、超时不交付、缺口必说明（`tests/test_acceptance.py::assert_red_lines`）。
3. **Trace 抽查**：人工核对 `examples/*.trace.json`，确认每步工具参数（含每版脚本）、观察结果与决策依据一致，可逐版 diff 压缩前后脚本。
4. **参考实例对拍**：用题目参考实例（P01 仅"支持字幕" + 30 秒 → 首稿超时 → 压缩 → 交付含分镜/P01 引用/总时长；无效数据不得添加"效率提升 80%"）作为金标准用例复现，见 `examples/over-duration.*` 与 `tests::test_7`。
5. **审核要点专项**：`tests::test_8` 改变目标时长（30→10 秒）与素材事实（增加"护眼屏幕"），断言下一步动作随之调整（交付↔明确失败）、分镜与引用随之改变，证明无场景硬编码。
6. **可复现性**：评审者按 README 命令从零运行，应得到与 examples/ 一致的结果（run_id 与时间戳除外）。

## 边界声明

- 仓库内不包含任何真实密钥；`.env.example` 仅列出变量名。
- Mock 模型是离线确定性策略，**它验证的是 ReAct 流程与工具协议，不证明真实模型效果**——这一边界同样适用于 examples/ 中的全部运行记录。
- 交付物仅为可编辑脚本，不执行真实发布（系统中无发布工具）。
