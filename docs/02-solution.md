# 02 - 方案（Solution）

设计方法遵循"通用 Agent 设计方法论"三板斧推导：**先拆材料与能力入口，再编排推理循环，最后定义评测与回流**。

## 一、调用流程

```text
用户请求（input.json：topic/target_duration/audience/platform/style）
  └─> CLI（src/main.py：输入文件校验，非法 JSON 非零退出）
        └─> ReAct 循环（src/agent.py，步数上限默认 12）
              ├─ 模型决策（src/model_client.py：Mock 策略 / OpenAI 兼容 API 双入口）
              │     动作 = tool_call(name, args) 或 finish(payload)
              │     脚本创作与修改是模型行为：脚本作为 estimate/check 的入参传递
              ├─ 工具执行（src/tools.py：素材检索 / 时长估算 / 规则检查，均为只读）
              │     观察结果（含异常转观察，错误恢复不终止循环）
              ├─ Trace 记录（src/trace.py：步骤/参数（含每版脚本）/观察/决策依据）
              └─ 循环直到 finish 或达到上限（返回 incomplete）
```

典型路径 3 次工具调用：`search_materials → estimate_duration(首稿) → check_rules → 交付`；超时长路径 4 次：`search → estimate(首稿 47 秒) → estimate(压缩稿 29 秒) → check → 交付`。

## 二、动态决策（ReAct 循环的核心）

模型不是走固定分支，而是根据**最近一次工具观察**调整下一步：

| 观察结果 | 下一步动作 | 最终状态 |
| --- | --- | --- |
| 缺 topic/target_duration | 直接结束并列出缺口，不调用工具 | `missing_input` |
| 尚未检索 | 按主题 `search_materials`（不凭空写产品事实） | — |
| 检索为空（第一轮） | 再次检索确认素材库是否收录 | — |
| 两轮检索均为空 | 请求用户补充素材（不编造） | `no_material` |
| 检索命中，尚未估算 | 基于 top1 素材事实创作**首稿** → `estimate_duration` | — |
| 估算 total_sec > 目标（首稿） | **压缩脚本**（精简钩子/结尾、收紧事实句包装）→ 重新估算 | — |
| 压缩稿仍超目标 | 明确失败：给出最短可得时长与缺口，不交付 | `cannot_meet` |
| 估算 ≤ 目标，当前版本未检查 | `check_rules(标题+全部旁白)` | — |
| 检查命中，当前版本未修正过 | 修正措辞（只动模板词，不动素材事实）→ **重新估算** → 复检 | — |
| 修正后复检仍命中 | 如实终止，需人工介入 | `failed` |
| 时长与规则均通过 | 交付脚本（分镜/总时长/来源 ID/风险） | `delivered` |
| 工具失败（failed/tool_error） | **重试同一步骤一次**；连续 2 次失败如实终止 | `failed` |

分支由**观察结果驱动**而非预设脚本：同一策略函数在不同目标时长下走出不同路径（90 秒直接交付、30 秒压缩后交付、10 秒明确失败），Trace（`examples/*.trace.json`）中每步 `observation` 与 `decision_basis` 记录"为什么走这条路"。**版本化自查**是关键细节：以"当前版本文本是否已检查过"决策（check 入参全文与当前版本比对），避免对旧观察重复修正导致死循环。

## 三、模块职责（对应第二板斧五模块）

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| Prompt（`prompts.py`） | 任务边界、事实纪律、时长/规则判断职责、输出契约 | 不承载长期流程与全部背景 |
| Agent Loop（`agent.py`） | 观察-行动循环、停止条件、错误恢复 | 不含业务判断，判断归模型 |
| Memory | 任务内状态：历史观察即记忆；脚本版本从工具入参恢复（与真实 LLM 保有上下文一致） | 不做跨请求长期记忆 |
| Skill | 不沉淀——一次性任务，流程未稳定重复 | — |
| Tool（`tools.py`） | 3 个原子工具：素材检索/时长估算/规则检查 | 不承载完整业务流程 |

**为什么不上多 Agent**：创作与自查串行、无并行子任务、无权限隔离需求、上下文短，单 Agent + 工具足够；按"单 Agent 失效信号"逐条检查均不命中。

## 四、技术取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | **原生实现**（不用 LangGraph/ADK 等） | 核心 Loop 仅 ~40 行，透明、零依赖，避免"用框架默认行为代替设计解释" |
| 语言 | Python 3.10+ 标准库 | 零第三方依赖；API 模式用标准库 urllib 调 OpenAI 兼容接口 |
| 模型入口 | Mock（默认）+ API 双路径 | 无 Key 时全链路可离线验证；**Mock 边界：以"任务+历史观察"为输入的策略函数，验证 ReAct 流程与工具协议，不证明真实模型效果** |
| 脚本生成 | 模型行为（非工具） | 题目指定工具只有检索/估算/检查三类；"LLM 写、工具查"是与真实架构一致的职责划分 |
| 估算实现 | 字数/语速 + 分镜固定开销（工具层读 brand_rules） | 规则化可解释、可复算；"估算 vs 目标"的对比与压缩决策留给模型侧 |
| 检索实现 | 中文 2-gram 重合度打分 + 名称加权（工具层） | 模拟真实检索容错的有限性；检索改进的决策留给模型 |
| 运行方式 | CLI | 最贴合测试自动化与 Trace 落盘 |
| 材料接入 | 本地 JSON + 工具按需读取 | 素材量小（3 个产品）且需精确 ID 引用；单进程本地工具，不需要 MCP |

## 五、权限与安全边界（第一板斧：模型不是安全边界）

- **编造产品事实在源头被阻断（结构保证）**：脚本由模板 + **素材 facts 逐字嵌入**组装，模板措辞不含任何产品事实；测试对每个事实分镜断言"旁白包含素材 facts 原文"，并断言全脚本无百分比断言（"效率提升 80%"在结构上写不出来——素材里没有这个数据）。
- **事实与判断分离（本题关键设计）**：estimate_duration 只按"字数/语速+开销"返回 total_sec 与逐分镜 breakdown，**不判断是否超目标**；check_rules 只报命中，**不判断如何改**。超时压缩、缺口计算（29−10=19）、措辞修正全部由模型完成——若工具层替模型判断，"有效修正"就成了预设分支。
- **时长与检查结果逐一对应（审核要点）**：交付脚本中每镜 `est_sec` 来自估算工具的 breakdown（测试断言分镜秒数之和 == total_sec），`based_on`/`sources` 标注素材来源。
- **结构性防越权**：系统中不存在发布/投放工具，只交付可编辑脚本；Prompt 同步约束"不得声称已发布"。
- **故障注入**：`inject.search_fail_once` 由输入显式声明（注入一次失败、重试成功），确定性复现工具失败场景。
- **审计**：全部工具调用（含每版脚本文本）进入 Trace，可逐版 diff。
